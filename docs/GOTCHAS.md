# Known sharp edges

Known sharp edges. Update this file when a new one is found — the gotcha journal is one of the most valuable artefacts in the repo.

1. **Headless GL on Linux is a known nuisance.** ModernGL needs an OpenGL context; in a container with no display server, you need EGL (`pyopengl-accelerate` + Mesa EGL drivers in the image) or osmesa. Budget extra time for the first successful render inside a container.
2. **Dagster K8s executor has sharp edges** around RBAC and service-account setup. Validate the executor against a local `kind` cluster *before* pointing it at real GKE — diagnosing pod-permission errors against the cloud is slow.
3. **Zarr v3 vs v2.** xarray supports both but the on-disk layout differs and they are not interchangeable. Pin to one in `requirements.txt` and stick with it across all stages, or stage-N's Zarrs won't open in stage-M.
4. **Zarr chunk shape is permanent.** Once a store is written with a chunk shape, you can't change it without rewriting. Decide `(1, H, W)` (frame-aligned, parallel-writable per frame) early in `common/store.py` and don't drift.
5. **xarray + dask + zarr write semantics.** `ds.to_zarr(..., region=...)` writes to a sub-region of an existing store, which is what enables parallel partition writes. Materialising into a freshly created Zarr from multiple workers without `region=` can corrupt chunks. Read the xarray "region writes" docs once before stage 04.
6. **Workload Identity Federation setup has a specific dance** — GitHub OIDC issuer → GCP workload identity pool → attribute mapping → service account impersonation binding. The official Google blog post is the cleanest walkthrough. Don't wing it from Stack Overflow answers.
7. **GKE Standard, not Autopilot.** Autopilot abstracts away the things you're trying to learn.
8. **`kubectl apply` from GitHub Actions** needs the `gke-gcloud-auth-plugin` installed in the runner. Easy to miss; error message is cryptic.
9. **Artifact Registry, not Container Registry.** GCR is in sunset.
10. **Skip a Cloud Load Balancer Ingress for the weekend.** Use `kubectl port-forward` for the demo — Cloud LBs cost ~$18/mo if you forget to delete one. Stage 12's viewer can deploy to Cloud Run instead — scales to zero, has its own URL, no LB needed.
11. **icechunk session lifecycle.** Open a session, write, *commit*. Forgetting to commit (or committing from the wrong process) is the rookie failure mode. Each Dagster job run = one commit; coordinate the commit through the orchestrator, not the partition workers.
12. **Stage 05 uses float32 throughout.** PyTorch's MPS backend has historically lagged on `complex128`, and CPU/GPU equivalence is easier if everything is float32 anyway. Implement stage 05 with separate float32 real and imag tensors, not complex dtypes. Useful zoom caps at ~10⁶ at float32; deep zoom lives in stage 06. Set `PYTORCH_ENABLE_MPS_FALLBACK=1` for any unimplemented ops.
13. **Docker Desktop on Mac doesn't pass through the Apple GPU.** Containers built for GKE's CUDA pool run on your Mac with software rendering (very slow). Use the container locally for "does it compile and start" checks; perf-test only on a real GPU node.
14. **`ZarrUserWarning: Consolidated metadata is currently not part in the Zarr format 3 specification`** is harmless and emitted on every `to_zarr(zarr_format=3)` call. xarray writes a consolidated-metadata file by default to speed up store opens; v3 has not standardised the format yet but reading and writing still work. Suppress at the test-runner level if it gets noisy, but don't disable consolidated metadata — opens get slower without it.
15. **Pod-per-frame is the wrong fan-out shape.** Tempting because the data is partitioned by frame; ruinous because Pod startup (~25 s) is ~500× per-frame compute. Partition by *Pod* — one partition per worker — and have each Pod loop over a contiguous frame range. The asset's `partition_key` is the Pod index, not a frame index. See [`FANOUT.md`](FANOUT.md) for the full reasoning and the math behind picking `n_pods` for a workload.
16. **`dagster asset materialize --partition-range` requires `BackfillPolicy.single_run()` or a running daemon.** Without one of those, the CLI refuses with a message about backfills. For local plumbing validation, loop one partition at a time via the CLI. For real cloud fan-out, you need either a deployed Dagster instance (`dagster-webserver` + `dagster-daemon`) or a small Python wrapper around `dagster.materialize()` that submits partitions in parallel. The CLI is fine for proving the asset code; it doesn't drive the executor's parallel path.
17. **`icechunk.Repository.open_or_create` is not race-safe across processes.** Two concurrent Pods both seeing "no repo" both try to create one and the result is undefined. icechunk logs a `WARN` about it on local FS. The fix is to pre-init the repo from a single process before fanning out — exactly what `stages/s09_zoom_fanout_cpu/run.py`'s dispatcher mode does. For Dagster on GKE, add a tiny `init_repo` script that runs before the materialise. **Separately**, naive `session.commit()` is also not race-safe — a Pod whose session opened on an earlier parent will get `icechunk.ConflictError` when another Pod commits first. For disjoint writes (different chunks), wrap commit in a rebase-on-conflict loop using `BasicConflictSolver`. See the pattern in `run.py::run_task` and the writeup in `RUNBOOK.md` failure-mode #2.
18. **Cluster node-pool size must match `n_pods`.** Each fan-out Pod on the default `e2-standard-2` consumes essentially one node's CPU. If `max_node_count < n_pods`, Pods queue and the fan-out serialises — no error, just slow. The autoscaling pool in `stages/s09_zoom_fanout_cpu/terraform/gke.tf` defaults `max=8` to match `n_pods=8`. Bump both together when scaling up.
19. **`max_iter` depth scheduling looks clever but isn't worth it.** Earlier prototype scaled `max_iter` with zoom depth (cheap outer, expensive deep). The compute savings are ~5–10 % at best because Mandelbrot's escape-on-radius plus cardioid / period-2 early-exit shortcuts make a high `max_iter` nearly free on outer frames where most pixels escape in <50 iterations anyway. Constant `max_iter` per preset is simpler and barely worse. (`common/config.py`.)
20. **Fractal colouring: put the gradient on the boundary, and don't normalise per-frame.** A global/linear normalisation spends most of its colour range on the flat fast-escape "sea" (most of the frame) and crushes the boundary filaments — the actual structure — into a thin slice; histogram equalisation fixes the contrast but allocates colour by *area*, same problem, and is also per-frame so it strobes in an MP4. The renderer instead uses a **cyclic palette keyed to `√(iteration count)`** (`render/palettes.colorize`): colour repeats as the count climbs, so variation concentrates wherever the count changes fastest (the boundary), and the mapping is per-pixel/stat-free, hence temporally stable — stills and animation share one function with no flicker. **Caveat:** stored iteration counts are integers, so very shallow views still band faintly. Truly smooth colouring needs the *fractional* escape value `n + 1 - log2(log|z|)`, which the data product doesn't store; the README banner recomputes it (large bailout radius ≈ 2¹⁶) for that one asset rather than colouring stored counts.
21. **GKE clusters default to `deletion_protection: true`** in the `hashicorp/google` provider since ~v5.0. `terraform destroy` fails with `Cannot destroy cluster because deletion_protection is set to true`. Set `deletion_protection = false` explicitly on `google_container_cluster` for any cluster you'll regularly rebuild. For production clusters leave it default and use `terraform state rm` if you ever really need to remove. The "out" if you forget is `gcloud container clusters update <name> --region <r> --no-deletion-protection` then re-run terraform destroy.
22. **When you benchmark "before vs after", make sure "before" didn't change too.** The s05 eager-vs-`torch.compile` comparison briefly showed a 6.7× compile win — because the refactor that introduced the compiled variant had also slowed the *eager* baseline (a `torch.tensor(k, device=...)` allocated per loop iteration = one host→device scalar copy per iteration; the original passed a Python scalar, which eager `torch.where` accepts transfer-free). The compiled path genuinely needs the on-device counter (a fresh Python int per call makes dynamo respecialise), but porting that pattern back into the eager path silently penalised the baseline and inflated the headline. Real win: ~1.2–2.3× on MPS. Caught because the committed `bench/results/kernel_throughput.json` history made the eager regression visible (0.43 s → 0.53 s for identical math). Keep benchmark JSONs in git; diff them when a "speedup" looks too good.
23. **Workload Identity pools soft-delete for 30 days — `terraform destroy` + re-apply 409s.** After a full teardown, re-applying the s09 stack fails on `google_iam_workload_identity_pool` ("already exists" — the deleted pool still holds the ID). Fix: `gcloud iam workload-identity-pools undelete github-pool --location=global` (same for the provider under it), then `terraform import` both back into state and re-apply. Renaming the pool instead creates litter — each abandoned ID stays reserved for its own 30 days.
24. **`backoffLimit: 0` + cluster autoscaler = a job that kills itself before nodes exist.** While the autoscaler is still bringing nodes up (zonal CPU quota makes this take minutes — gotcha for new projects), early Pods get preempted/evicted by scheduler churn; each such death counts as a Pod *failure*, so a zero/low backoff budget burns out before any real work starts (portfolio-stride-001 died 46s after dispatch with healthy code). The fix is not a bigger backoffLimit alone — it's `podFailurePolicy: {rules: [{action: Ignore, onPodConditions: [{type: DisruptionTarget}]}]}`, which exempts infra disruptions while real app crashes still fail fast. Diagnose from Cloud Logging events (`jsonPayload.reason=~"FailedScaleUp|Preempted"`) — the Pods themselves are GC'd by the time you look.
